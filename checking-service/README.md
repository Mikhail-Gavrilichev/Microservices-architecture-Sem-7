# Вердикт — микросервис проверки работ

Учебный проект: **один** ASP.NET Core 8 Web API-проект, Entity Framework Core + **собственная PostgreSQL**, статический frontend на HTML/CSS/JavaScript, Nginx и Docker Compose. Нет общей базы с микросервисом подготовки форм, брокера и авторизации.

Фронтенд — рабочее место жюри: одна работа на экран, ответ участника и эталон рядом, две кнопки и клавиши `1`/`2`. Backend, API, модели, DTO и миграции при доработке интерфейса не изменялись.

## Запуск

Из **корня репозитория** (единый Compose для обоих микросервисов):

```bash
docker compose up --build
```

* Frontend: **http://localhost:8091**
* Swagger: **http://localhost:8091/swagger** (или http://localhost:8090/swagger)
* Health: **http://localhost:8090/api/health**

Backend подключается к PostgreSQL по `Host=checking-db`. База `checking_db` и фотографии `/app/photos` лежат в **двух именованных Docker volume**, отдельно от других проектов. Compose ожидает healthcheck PostgreSQL. В учебном запуске работает один backend: миграция применяется до старта HTTP-сервера. `docker compose down` сохраняет данные; `docker compose down -v` удаляет оба volume. Пароль по умолчанию учебный, задаётся переменной `CHECKING_DB_PASSWORD` **перед первым запуском**; в рабочей среде нужен секрет и настоящая авторизация.

## Вход без авторизации

Регистрации, паролей, JWT, OAuth и backend-авторизации нет. На первом экране спрашивается **«Кто вы?»**: имя и роль, кнопка «Войти». Выбор хранится в `localStorage`, кнопка «Сменить пользователя» возвращает к экрану входа. Ничего не отправляется на сервер.

| Роль | Интерфейс |
|---|---|
| Участник | отправка решения, загрузка и подтверждение фото |
| Жюри | экран быстрой проверки |
| Старшее жюри | то же + переданные (эскалированные) работы |
| Организатор | тестовые работы, жюри, очередь, результаты |

Настоящий backend по-прежнему требует `JudgeId`: если члена жюри с введённым именем нет, в шапке появляется кнопка «Создать члена жюри «Имя»» — это обычная функция сервиса, а не авторизация. Тестовые работы доступны без неё.

## Экран проверки (5 секунд на работу)

Одна работа на экран: слева ответ участника и фотография, справа эталонный ответ, снизу две крупные кнопки.

| Действие | Клавиша / элемент |
|---|---|
| Зачёт | `1` или кнопка «Зачёт» |
| Незачёт | `2` или кнопка «Незачёт» |
| Предыдущая / следующая работа | `←` / `→` |
| Передать старшему (только назначенная работа) | небольшая кнопка внизу |

* После оценки работа сразу открывает следующую — без подтверждений, диалогов и перезагрузки.
* Уже проверенная работа помечается в шапке («✓ уже проверено: зачёт»), кнопки блокируются — случайно оценить дважды нельзя.
* Счётчик `проверено / всего` и тонкая полоса прогресса; текущая работа и прогресс сохраняются в `localStorage` и восстанавливаются после перезагрузки.
* В DOM всегда одна работа, поэтому 2500 работ не замедляют интерфейс (≈3 мс на переключение в тестах).
* Работы приходят с сервера последовательно: только свои назначения: обычному жюри — первичные, старшему — явно переданные. Завершение проверки освобождает жюри, сервер сам назначает следующую работу.

## Тестовые работы (только фронтенд)

Кнопка «Создать 100 тестовых работ» (на пустом экране жюри или в панели «Организатор») создаёт 100 решений в `localStorage` и **не делает ни одного запроса на backend**:

* часть ответов совпадает с эталоном, часть отличается;
* каждое 12-е решение содержит тестовую «фотографию» формы (SVG data URL), остальные — плейсхолдер;
* данные идут через тот же экран проверки, что и реальные;
* «Очистить тестовые работы» удаляет работы и их оценки, «Сбросить прогресс проверки» — только оценки.

## Фотографии

`PhotoUrl` из API (`/api/checks/{id}/photo`) отображается в интерфейсе жюри и в очереди организатора:

* путь нормализуется: `/api/...`, `api/...` и абсолютный внутренний URL (`http://backend:8080/api/...`) приводятся к относительному пути через nginx; `data:` и `blob:` используются как есть;
* клик по фотографии открывает увеличение (клик или `Esc` — закрыть);
* нет фотографии — плейсхолдер «Фотография не приложена»;
* ошибка загрузки — сообщение, кнопки «Повторить» и «Открыть отдельно» вместо пустого блока;
* при подтверждении читаемости участник видит предпросмотр только что загруженного файла (раньше фотография в этот момент вообще не показывалась, а до создания проверки отдельного маршрута выдачи фото в API нет — backend не менялся).

## Как пройти сценарий

1. http://localhost:8091 → роль **Участник** → выберите форму из выданного в первом сервисе комплекта, введите ответ. Используйте корневой Docker Compose.
2. Нажмите «Загрузить фото», выберите **настоящее изображение JPEG/PNG** и укажите номер формы (`PhotoFormId`). Затем «Проверить фото» → отметьте «Фото читаемо» и «Ответ виден» → подтвердите. При отрицательном подтверждении решение получает `PhotoInvalid`: «Отправить повторно», исправить ответ, загрузить новый снимок.
3. **Сменить пользователя** → роль **Жюри**, имя, например, «Анна» → при необходимости «Создать члена жюри». Работа откроется на экране проверки: условие, ответ участника, эталон, фотография **без TeamId**.
4. `1` — зачёт (сервер получает `accept` + `complete`, 1 балл), `2` — незачёт (0 баллов). Следующая работа появится автоматически после освобождения жюри.
5. **Эскалация обычным жюри:** внизу экрана «Передать старшему» — работа станет `Escalated` и уйдёт свободному старшему жюри; если старший занят, она останется в очереди эскалации.
6. **Организатор → Результаты:** появится сохранённая запись. Повторное завершение невозможно. Результат содержит `SubmissionId`, по которому отдельный сервис подсчёта свяжет его с командой.

### Важное упрощение проверки формы

Сервис читает выданные формы и эталон по HTTP, не обращаясь к чужой БД. Проверка фотографии выполняется здесь: сверяется номер формы, файл декодируется как JPEG/PNG; читаемость подтверждается вручную, без OCR.

## API

Статусы: решения — `Created`, `PhotoAttached`, `PhotoInvalid`, `AcceptedForChecking`, `Completed`; проверки — `Queued`, `Assigned`, `Accepted`, `Declined` (переходное состояние), `Escalated`, `Completed`. Роли — `Judge`, `SeniorJudge`. Ошибки бизнес-логики — JSON `{ "error": "..." }`, HTTP 400/404/409; ошибки обязательных полей — стандартный ответ ASP.NET Core 400.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/catalog/forms` | Каталог выданных форм **без** правильных ответов |
| POST/GET | `/api/submissions` | Отправить / список решений |
| GET | `/api/submissions/{id}` | Решение и статус (без правильного ответа) |
| POST | `/api/submissions/{id}/photo` | `multipart/form-data`: `file`, `photoFormId` |
| POST | `/api/submissions/{id}/validate-photo` | `{ "isPhotoReadable": true, "isAnswerVisible": true }`; создаёт запрос проверки и назначает работу |
| POST | `/api/submissions/{id}/resubmit` | `{ "answer": "Исправленный ответ" }` после `PhotoInvalid` |
| POST | `/api/checks` | `{ "submissionId": 1 }`; идемпотентно возвращает уже созданную при подтверждении проверку |
| GET | `/api/checks/queue`, `/api/checks/{id}` | Очередь / работа жюри (без TeamId) |
| GET | `/api/checks/{id}/photo` | Снимок для жюри |
| POST | `/api/checks/{id}/assign` | `{ "judgeId": 1 }` для ожидающей работы |
| POST | `/api/checks/{id}/accept`, `/decline` | `{ "judgeId": 1 }`; отказ автоматически передаёт старшему |
| POST | `/api/checks/{id}/escalate?seniorId=2` | Повторно назначить ожидающую эскалацию старшему; параметр необязателен |
| POST | `/api/checks/{id}/complete` | `{ "judgeId": 2, "isCorrect": true, "pointsAwarded": 1, "comment": "Верно" }` |
| POST/GET | `/api/judges` | Создать / список членов жюри |
| GET | `/api/judges/{id}/checks` | Работы жюри без TeamId |
| GET | `/api/results`, `/api/results/{id}` | Неизменяемые результаты |

Пример создания жюри: `POST /api/judges` с телом `{ "name": "Анна", "role": "Judge", "isAvailable": true }`. Один член жюри имеет не больше **одной активной проверки** — правило проверяется сервисом и частичным уникальным индексом PostgreSQL. При одновременных запросах конфликт возвращает 409.

Без Docker можно задать `ConnectionStrings__Default` и выполнить `dotnet run --project CheckingService`. Для следующих миграций: `dotnet ef migrations add Название --project CheckingService --output-dir Data/Migrations` (нужен dotnet-ef версии 8).
